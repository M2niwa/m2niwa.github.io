断线重连策略：从 3 秒轮询到指数退避

2025-08-25

写完 FastAPI + WebSocket 实时仪表盘之后，我最先犯的错误就是「断线就 3 秒后重连」。白天看着没问题，电脑合盖一晚上，仪表盘的日志里躺了三百多行重连记录——服务器端每轮重连都新建一条连接，旧的又没真正销毁，两天后把本地服务的内存吃掉了 200MB。

为什么固定间隔重连是错的

问题有两层。第一层是客户端：固定 3 秒重试，等于在服务器没恢复的时候用密集请求打自己。反过来，网络已经恢复时又不一定正好赶上那 3 秒，用户要平白多等一等。第二层是协议层：浏览器 WebSocket API 直接暴露的只有 send()，RFC 6455 定义的 Ping/Pong 控制帧浏览器并不让你手动发（参见 RFC 6455 §5.5.2 与 MDN 的 WebSocket 文档），所以「连接还活着吗」只能用应用层消息探活——这正是很多僵尸连接一直霸占服务器资源的原因。

web.dev 的《Reconnecting WebSockets in Practice》总结的解法是：指数退避 + 抖动。重试间隔从短到长，但每次加一个 30% 左右的随机抖动，避免多设备同时断线后同一时刻齐刷刷地撞服务器。

带抖动的指数退避，一个能用的实现

let attempt = 0;
let heartbeat = null;

function connect() {
  const ws = new WebSocket('wss://' + location.host + '/ws');

  ws.onopen = () => {
    attempt = 0;
    heartbeat = setInterval(() => ws.send('ping'), 30000);
  };

  ws.onclose = () => {
    clearInterval(heartbeat);
    const base = Math.min(30000, 1000 * Math.pow(2, attempt++));
    const delay = base * (0.5 + Math.random() * 0.5); // ±50% jitter
    setTimeout(connect, delay);
  };

  ws.onerror = () => ws.close(); // 让 onclose 统一收口
}
document.addEventListener('visibilitychange', () => {
  if (document.hidden) ws.close();
  else { attempt = 0; connect(); } // 回到前台立即重连
});

两个细节值得说明：ws.onerror 只管触发 onclose，重连逻辑只写一处；visibilitychange 时主动关闭连接，是因为浏览器切后台后连接常被挂起，僵尸连接会一直占住服务端的推送循环——这也是 博客 3 里仪表盘断线重连总在后台标签页捣乱的原因。

实测效果：断网 10 分钟内的重试次数从固定的 200 次降到 25 次，恢复网络后平均 2 秒内就能重新推上数据。服务器端再配一轮 5 秒的孤儿连接清理（收到的消息超过 30 秒没新数据就关闭），内存曲线就彻底平了。真正的重连策略从来不是「重试」，是「别让重试伤害服务器」。
