个人站上 Cloudflare Pages：网络路径与 SPA 回退配置

2026-04-08

这个站的部署史是一条清晰的时间线：最开始按建站记里的方案跑在本机 Windows + Uvicorn 上，然后推到 GitHub Pages 走国外访问，最后把主站钉在 Cloudflare Pages 上作为国内可达的入口。这次迁移让我把「静态站托管」背后的网络路径真正看清楚了。

Git 集成与全球网络

Cloudflare Pages 的部署方式是连接 Git 仓库主干分支，代码一推就自动构建，构建配置留空就行——我连 API Token 都没生成过，因为根本用不到（Cloudflare 文档称这套为「Framework guides + Git integration」，Pages 托管在其全球网络上）。真正的差别在网络层：Cloudflare 用 Anycast 把每个访客路由到最近的边缘节点，静态资源在你眼皮底下命中缓存；但免费版没有中国内地节点，从大陆访问会绕行境外线路，速度波动比我预想的大，高峰时段甚至不如直连 GitHub Pages 稳定。好处是它不经过需备案的境内线路，作为个人站合规成本为零。

所以最终布局是两个域名并行：GitHub Pages 作为国外镜像，Cloudflare Pages 作为主站，DNS 都指向 m2niwa.pages.dev——结构上只多一个同构仓库，收益是大陆与海外都有了稳定的入口。

两条值得抄进仓库的配置

Pages 的根目录放 _redirects 和 _headers 两个文件就能声明回退与缓存策略。个人单页站最有用的是 SPA 回退：

# _redirects —— 未知路径回退到首页（SPA 路由）
/*  /index.html  200

# _headers —— 静态资源和 PDF 长缓存
/blog/*
  Cache-Control: public, max-age=86400
/*.pdf
  Cache-Control: public, max-age=604800

第一条把任意未知路径 200 回退到主索引，第二条看着不起眼，但 8MB 的作品集 PDF 全靠它避免每次访问都全量重下——效果等同于本文的断线重连策略那篇文章里说的「不要让重复请求伤害别人」。另外提一句：Pages 的 404 页可以自定义，配一个 /404.html 会让 SEO 体检报告干净很多，这个比追着改路由有效得多。

回头看我唯一的失误是低估了「多站点认知成本」：GitHub Pages、Cloudflare Pages 和本地版三处同构，任何一处忘同步都会出现「改了本地，线上没变」的灵异现象。所以现在我把兼容脚本放进了仓库根目录，每次发布跑一遍，网络路径的事就交给边缘节点了。
